## Product findings from this inspection

1. **Selection is currently a host limitation.** Our scoped adapter fixes one
   persona per workspace. Task tags alone do not activate a migration sona.
   Existing constraints must not be mislabeled as the new candidate. A later
   adapter decision must explicitly select a versioned persona within the
   existing repository/store binding; do not silently replace the shared
   continuity persona for every task or bypass the host via ambient discovery.
2. **Derivation is not consumption.** We can inspect applicable constraints, but
   the current host declares shadow mode and no run/application outcome. Direct
   agent use must be recorded as an observed agent decision, not Runner-governed
   execution or automatic enforcement. A lightweight work log can record that
   distinction; a new enforcement framework is not a prerequisite.
3. **Output cost is visible.** The effective-persona response duplicates large
   provider/evidence payloads around a small constraint set; our attempted full
   read was truncated at the tool-output budget. Need a compact guidance view
   plus a retrievable full receipt. Claim no latency or token improvement until
   measured. This finding concerns the scoped host surface, not proof that the
   core cannot derive compact snapshots.
4. **The same lesson was already available.** continuity-first_stfc already says
   to preserve the task before a tangent. Recent drift therefore cannot be
   attributed solely to missing instructions. The new pilot must evaluate
   retrieval, salience and actual decisions, not reward an attractive manifest.
5. **Scope is narrower than an entire skill.** A sona describes decision style.
   The skill also contains repository routing and a repeatable procedure. Full
   skill replacement is viable only if those useful procedural parts have an
   authoritative, discoverable repository home without duplicate manuals.
6. **Authoring feedback needs alignment.** The installed2.0.4 public loader
   rejected the first draft because triggers was absent, while its next-action
   message listed required fields as id, version and behavior. Added a single
   explicit phrase alias; this does not imply automatic task selection. Prefer
   errors/examples that expose the complete minimal explicit-selection manifest.

## Smallest meaningful comparison

Keep the skill available as rollback. Before the next contained alignment
feature, select the delivery path explicitly. Do not call a prose-only trial a
live LexSona trial if task-specific selection remains unsupported by the host.

Use the same pinned source, feature-contract template and inventory for both
conditions. Existing skill-guided batches provide a qualitative baseline;
different feature difficulty and increasing agent familiarity prevent causal
performance claims. A later matched task can compare identical prose guidance
against LexSona delivery if added product value remains unclear.

For the sona condition, omit the full skill from the working instructions:
consume only the verified candidate constraint set plus the authoritative repo
procedure/evidence links. Pin persona content and version. Freeze learning for
the pilot; review any proposed correction before a later candidate revision.
Do not change product code to manufacture a tangent or failure.

Observe decisions and friction as they occur:

| Question | Evidence to retain |
| --- | --- |
| Was the intended sona selected and guidance actually read? | Exact persona/version/digest, task context, derivation receipt and concise consumption record |
| Did source preservation improve? | Source obligations, target mapping, omitted operations found before/after implementation |
| Were bug fixes kept distinguishable from parity? | Classified discoveries and task/return-point decisions; useful authorized tangents remain allowed |
| Were native experiments informative? | Hypothesis, diagnostic reachability and actual intervention observed; no forced in-game trials just to exercise the sona |
| Did it reduce repetitive work? | Repeated source scans/tests, context size and authoring/selection effort where recorded; no retrospective invented timings |
| Could another session resume? | Contract/inventory/recovery consistency and the next agent's actual retrieval needs |
| Was the extra machinery worthwhile? | Failures, ambiguity, irrelevant guidance, maintenance and context overhead versus decisions improved |

Success requires preserved behavior and useful decisions, plus a workable
selection/consumption path. Valid YAML, a derived receipt, successful compilation
or agent self-report alone does not establish success. One pilot can establish
feasibility and concrete friction, not general superiority. Retain, revise or
reject the replacement based on those observations.

## Next boundary

History follow-up: Git blame attributes the exact-one-persona-per-workspace
check to control-workspace commit00ff7bd (2026-08-24), "feat: bind LexSona to
scoped PostgreSQL". It was introduced with that scoped host integration, not
with this migration pilot. Current unrelated host changes do not add the limit.
This is an adapter selection restriction, not a one-persona-per-repository
restriction in LexSona's canonical API. That API accepts an explicit personaRef
when connecting within the authorized scope; a connection's persona is pinned,
and a separate connection can select another authorized stored persona revision.

A supported improvement is an allowlisted request-local persona reference in
the scoped adapter, preserving the existing continuity persona as the default.
Require exact declared version/revision/content, keep the same repository/store
binding, and reject unknown or ambiguous selection. Do not fake another
workspace, toggle a global active persona per task, bypass the adapter with an
ambient database path, or silently reinterpret task tags as activation. This
requires a bounded adapter change and registered persona revision; current MCP
arguments alone cannot express it. No such change was made during the study.

Review this candidate and the selection limitation before changing live persona
configuration. The next bounded product question is whether the existing scoped
host can legitimately select a task-specific persona with compact output while
preserving its current authority and continuity contracts. No host implementation
or control-workspace cleanup is part of this inspection. Primary-action work
remains parked; its diagnostics must be isolated before an ordinary build.
